# Rejected requests

Use the project's existing decision record. If it maintains `.out-of-scope/`, match requests by concept and read the relevant decision before treating the new request as equivalent.

For an authorized rejection, record the concept, durable reason, relevant constraints and links to prior requests. Append to an existing decision for the same concept instead of creating a file per issue. Use a short, descriptive filename.

Distinguish:

- **Rejected feature:** an explicit scope decision, suitable for this record.
- **Already implemented:** point to the working behavior; do not record it as a rejected feature.
- **Deferred work:** lack of time or a dependency is not a permanent rejection.

An existing decision is context, not automatic permission to close a new issue. Apply comments, labels and closures only within the user's authorized scope. If the maintainer changes the decision, update the record as requested; do not reopen historical issues automatically.
