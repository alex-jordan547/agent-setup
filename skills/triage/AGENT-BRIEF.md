# An actionable implementation brief

A brief should let a fresh contributor verify the request without reconstructing the conversation. Use the project's existing issue template where available.

Include:

- **Request and evidence:** the bug or desired behavior, with reproduction results or source links. Distinguish confirmed observations from assumptions.
- **Current and desired behavior:** enough context to identify the affected flow and its boundaries.
- **Contracts and pointers:** relevant interfaces, documentation, code locations and prior decisions. A path is a navigation aid, not a substitute for describing the behavior.
- **Acceptance criteria:** observable outcomes and how to check them, including the failure case that motivated a fix.
- **Scope:** exclusions, real blockers and any unresolved choice needing a maintainer.

For an external PR, describe what its diff already provides and the remaining gaps; do not ask for the entire feature to be rebuilt. Link existing evidence instead of duplicating it. Prepare the brief locally unless posting it is authorized.
